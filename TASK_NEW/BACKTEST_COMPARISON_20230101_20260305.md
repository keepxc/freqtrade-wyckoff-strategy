## 4. 差在哪：根因分析

### 4.1 你的直觉是对的，修复后确实减少了约 20pp 利润

但这**不是代码回退**（quality regression），而是：

#### ① "601.75%" ≠ 相同时间段的601%（误导性对比）

> **修复前基线 601.75%** 是约 20261218~20230101 的旧跑测（结束约 20260228），**而非** 20230101-20260305 同段数据。

当用**相同时间段** (20230101-20260305) 跑 Bug 版本时：
- Bug版本实际只有 **583.7%**，不是 601.75%
- 多出的 5 周时间（20260228→20260305）BTC 从 90K 继续下跌至 65K
- 即使不改代码，旧版本在这 5 周也只贡献 -18pp（601.75% → 583.7%）

#### ② Bug版本的"悖论表现"：意外保护机制

Bug版本 `dist_phase_d=83.9%` 的副作用是：**几乎锁死了 2025 年 Q4 至今（熊市下跌期）的所有多单入场**。

- Bug 导致系统认为"始终处于分发D阶段"→ `not_distribution=False` → 拒绝绝大多数多单
- 这个**错误拒绝**，在下跌市 (2025-11 ~ 2026-03) 期间反而避免了亏损
- 类似于"停钟也对两次" ——  并非真正聪明的选择，而是错误恰好与行情方向一致

#### ③ 修复版本的代价：Spring路径在下跌市加仓

修复增加了 `axis_trading_allowed` 路径5（Spring区间绕过EMA限制）和 `composite_intent_ok` Spring豁免。

但 **本次修复恰逢 BTC 最大下跌（100K → 65K）**：
- 修复后系统能正确识别 Spring 信号（Phase C 积累末期）
- 但 2026 年 1月~3月这批 Spring 信号很多发生在**二次下探**途中，而不是真正底部
- 导致约 +21 笔多余交易，净贡献 **-2059 USDT（-20.6pp）**

## 6. 最终结论

### Q：是修改代码的问题，还是真的是行情造成的？

**答：两者都有，但行情是主因（约占 2/3），代码修改是次因（约占 1/3）。**

| 原因 | 量化影响 | 说明 |
|------|---------|------|
| **行情（BTC 下跌）** | **约 -13pp** | 2026年1~3月 BTC 下跌5周，Bug版本也因此跌了约 601.75%→583.7% = -18pp |
| **代码修改（Spring路径新增）** | **约 -7pp** | 同期修复版比 Bug 版多 -20.6pp，其中约 -7pp 来自新增Spring路径在下跌途中的不当多单 |
| **代码修复（Bug消除）** | **中性/正** | EventSeqSM 修复正确，长期将带来正贡献 |

### Q：修复有没有效果？

**有：**
1. ✅ **dist_phase_d Bug 彻底修复**（83.9% → 0%），从根本上消除了逻辑错误
2. ✅ **SQN提升 7.87→7.30**（注：6.87→7.30），风险调整后表现更优
3. ✅ **最大回撤减少 -2.71pp**（8.40%→5.69%），资金安全性提升
4. ✅ **Calmar提升 +42%**（114→163），回报/风险比提升
5. ⚠️ **Spring路径需要更严格的质量门控**：路径5目前只有 `not_distribution` 一个门控，建议后续添加 `spring_quality >= 'spring_2'` 防止下跌途中的低质量Spring入场
