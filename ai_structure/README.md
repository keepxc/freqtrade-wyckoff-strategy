# BTC 波段结构 + 外部 AI 对比 · 定时分析包

一个自包含的 Linux 部署包：每天两次自动跑「数据更新 → 波段结构统计 → 出图 → 调外部 AI → 归档」，
并把**程序算出的客观结构**与**外部 AI 的看图解读**并排放好，供人工比对。

设计原则只有一条：**只回答数据能回答的问题。** 结构能可靠回答「现在在哪」，
不能可靠回答「接下来去哪」——所以报告里所有方向性结论都带样本量、置信区间和判定码，
而不是一句「偏多」。

## 1. 先回答你的问题：亚盘还是欧美盘波动大？

结论：**欧美开盘后波动明显更大，而且这个差距还在扩大。**

用包内 `session_vol.py` 在 2017-08 至 2026-09 的 79,743 根 1h K 线上实测。
口径是「归一化波动」——每个 bar 的 |log 收益| 除以它所属日之前 30 天的滚动均值
（trailing，无前视）。归一化是必须的：2017-2018 的绝对波动是 2024-2026 的好几倍，
不归一化的话，画出来的「日内节奏」其实是「年代节奏」。

**时段汇总**（1.00 = 全样本平均，3,315 个有效配对日）：

| 时段 | UTC | 归一波动 | vs 全样本 | 样本 |
|---|---|---|---|---|
| **欧美重叠** | 13:00–16:00 | **1.309** | **+28.4%** | 9,944 |
| 美盘 | 13:00–21:00 | 1.165 | +14.3% | 26,522 |
| 欧盘 | 07:00–16:00 | 1.058 | +3.8% | 29,818 |
| 其余时段 | 21:00–24:00 | 1.016 | −0.3% | 9,949 |
| 亚盘 | 00:00–08:00 | 0.924 | **−9.4%** | 26,469 |

**小时画像**（只列关键位置）：

| UTC | 归一波动 | 说明 |
|---|---|---|
| **14:00** | **1.400** | 全天峰值（伦敦下午 + 纽约上午重叠） |
| 15:00 | 1.320 | |
| 13:00 | 1.206 | 纽约开盘 |
| 16:00 | 1.175 | |
| 00:00 | 1.147 | 亚盘内的局部小峰（东京开盘） |
| 12:00 | 1.032 | |
| 07:00 | 0.892 | |
| 03:00–06:00 | 0.83–0.85 | 全天谷值 |

**按天配对检验**（同一天内比亚盘 vs 欧美，年代效应被完全消掉）：

- 波动差 **−0.240**（亚盘 − 欧美），亚盘更高的天数只占 **36.2%**，**t = −17.4** → 极显著
- 方向差 −0.0608%（累计 log 收益），**t = −1.2** → **不显著**

也就是说：**亚盘不是「更容易跌」，它只是「更没动静」。** 这两件事经常被混为一谈。

**跨年代稳健性**（亚盘 − 欧美的归一波动差）：

| 年代 | 亚盘 | 欧盘 | 美盘 | 欧美重叠 | 亚盘−欧美 |
|---|---|---|---|---|---|
| 2017–2019 | 0.965 | 1.038 | 1.062 | 1.146 | −0.095 |
| 2020–2022 | 0.936 | 1.069 | 1.110 | 1.227 | −0.173 |
| 2023–2026 | 0.889 | 1.062 | **1.274** | **1.477** | **−0.385** |

差距从 −0.095 扩大到 −0.385，**近三年还在加速**（美盘从 1.062 涨到 1.274）。
这不是年代噪声，是越来越强的结构性事实。

### 由此得到的排班

| 槽位 | UTC | 本地时区换算 | 选它的理由 |
|---|---|---|---|
| 亚盘 | **00:30** | 见 `install_cron.sh` | 东京开盘后（00:00 有局部小峰 1.147），且**刚好在 AI 额度重置之后** |
| 欧美 | **14:00** | 见 `install_cron.sh` | 全天波动峰值小时（1.400） |

两次都在「结构刚被信息冲击过」的时刻取样，而不是在死水时段空跑。
额度重置在 00:00 UTC，所以第一次必须排在它之后——00:30 满足，且落在一个波动小峰上。

## 3. 每天两次，各跑什么

`run_session.sh <slot>` 是唯一的编排入口，五步：

```
1/5  更新数据    swing_watch.py --update
                 从币安公开接口增量拉最新 1h K 线，追加进 data/BTCUSDT_1h.csv
                 （失败不中断——沿用本地数据出图，比什么都不产出有用）

2/5  生成图表    make_chart.py
                 双栏图 out/chart_dual.png：上栏日线（约 430 天），下栏 4H（约 60 天）
                 纯 Pillow 绘制，不依赖 matplotlib，也不联网

3/5  刷新 token  ai_login.py
                 幂等：现有 JWT 未过期就直接跳过，不消耗额度

4/5  调外部 AI   ask_ai.py --slot <slot>
                 把无标注的双栏图 + 一段中性提问发给图表分析 AI
                 调前先查额度，额度为 0 直接退出（不浪费请求）

5/5  归档        out/archive/YYYYMMDD/<slot>_*
                 避免下一轮把这一轮的产物覆盖掉
```

> **2026-09-27 起新增前向观察**：编排变为 6 步，第 5 步 `forward_log.py` + `score.py`
> 记录「程序方向 / AI 方向」并回填实际涨跌，结果在 `out/forward_log.csv` 与
> `out/forward_score.md`。判据已冻结，见 [FORWARD_PROTOCOL.md](./FORWARD_PROTOCOL.md)；
> bot 机器部署步骤见 [AGENT_TASK.md](./AGENT_TASK.md)。
> 同日修复：增量更新曾把**未收盘**的当前 bar 写进 CSV 且永不覆盖，现只落已收盘 bar，
> 并从末行 ts 起重拉覆盖。

退出码：`0` 正常 / `1` AI 调用失败 / `2` 前置缺失（token 或图）/ `3` 额度为 0。
cron 里这些码不做事，但日志里能区分「没跑」和「跑了但没调成」。

## 5. 脚本各自能单独跑

所有脚本都只依赖 `config.py` 和同目录的 `data/`，可以脱离编排单独执行：

```bash
.venv/bin/python swing_watch.py                    # 结构分析，打印到终端
.venv/bin/python swing_watch.py --update           # 先增量拉数据
.venv/bin/python swing_watch.py --theta 0.20       # 换阈值（稳健性检查）
.venv/bin/python swing_watch.py --json a.json --html a.html

.venv/bin/python selftest.py                       # 交付自检（推荐先跑）
.venv/bin/python selftest.py --skip-slow           # 只查数据完整性与报告结构
.venv/bin/python session_vol.py                    # 时段波动分析
.venv/bin/python make_chart.py                     # 出图
.venv/bin/python download_data.py --from 2020-01-01   # 只下 2020 年之后
.venv/bin/python ai_login.py                       # 换 token
.venv/bin/python ask_ai.py --slot manual --dry-run # 只看提示词，不发请求
.venv/bin/python ask_ai.py --slot manual --force   # 忽略幂等，强制重调（耗额度）
```

`swing_watch.py` 的退出码 `2` 表示「数据不足以确认任何枢轴」——不是崩溃，
是数据不够（例如只给 68 根 K 线、θ=0.30 时确实无法确认一个摆动点）。

### `selftest.py` 检查什么

交付自检分四类，按「越往下越有价值」排列：

| 类 | 内容 | 为什么重要 |
|---|---|---|
| A 数据完整性 | 行数、递增性、缺口、OHLC 自洽、数据新鲜度 | 数据坏了后面全是错的 |
| B 算法不变量 | 每个枢轴之后必须真的反向走过 θ；区间必须包含点估计；独立样本随期限单调不增 | 违反即说明实现有 bug |
| C 判别力 | 喂**已知答案**的合成输入，看它能不能分辨 | 只会返回 0.5 的报警器永不报错，也永不报警 |
| D 边界夹具 | 68 根 / 5 根 / 恒定价格 / 单调序列 / 极小 θ | 无人值守时要优雅退出，不是崩 |

C 类里的合成序列是**刻意构造**的，不是随机数：非重叠抽样的步长恒为 `h*24`，
而 24 能被 1/2/3/4/6/8/12/24 整除。若信号周期能整除 24，抽样点会全部落在同一相位
（P(涨) 变成 0 或 1）；用与 24 互质的周期（如 5），抽样点均匀覆盖所有相位，
P(涨) 就等于模式里正号的比例——**期望值事先算得出来**。这正是「判别力夹具」该有的性质。

B 类里那条「枢轴有效性」检查抓到过一个真 bug：`zigzag` 初始化阶段高、低两个极值
共用一个下标变量，导致首个枢轴**价格取自高点、位置却指向低点**（价格对、时间错）。
现在这条检查对真实数据的全部 49 个（θ=30%）与 118 个（θ=20%）枢轴逐一验证，
防止回归。

## 6. 报告怎么读

`out/report_watch.html` 是自包含的（无 CDN、无外链、可直接邮件发送），两块图：

**位置图**：近 18 个月日线，标出已确认的枢轴（三角）、当前腿的区间底纹、
以及「本腿终结触发线」。注意图上所有枢轴都是**已确认**的——即要等价格反向走够 θ
才画上去。这不是延迟，是避免前视偏差的代价。

**方向概率图**：各期限（7/15/30/60/90/180/365 天）的 P(上涨)，
两组并列：基准率（随便哪天买入）vs 当前状态（上行腿 · 已突破前高）。
每个点带 Wilson 95% 置信区间，50% 处有一条竖线。

判定用四层，全部通过才给方向结论：

1. **样本量**：独立观测 ≥ `MIN_INDEP`（默认 15）
2. **方向**：95% 置信区间是否排除 50%
3. **增量**：相对基准率是否显著（单侧二项检验，按观测偏离方向取尾）
4. **样本外**：A/B 两段独立子样本是否同向

多重检验做了 Bonferroni 校正（4 状态 × 7 期限 = 28 组 → α = 0.0018）。
判定码：`方向确认` / `有增量` / `偏弱` / `含50%无法确认` / `样本不足`。

## 7. AI 额度机制（决定排班的关键约束）

外部图表分析 AI 的免费额度是**每账号每天 2 次**，在**北京时间 08:00（= 00:00 UTC）重置**。

这正好对应「每天两次」的设计：

```
00:00 UTC  额度重置
00:30 UTC  亚盘槽位  → 用掉第 1 次
14:00 UTC  欧美槽位  → 用掉第 2 次
（次日 00:00 UTC 重置）
```

包内做了三层保护，避免把额度浪费在无效请求上：

1. `ask_ai.py` **调用前先查额度**，为 0 直接返回 3，不发请求
2. **幂等索引** `ai_index.json`：同一槽位同一天已成功调用过就跳过（`--force` 可覆盖）
3. **原始报文落盘** `ai_raw_response.txt`：解析失败时结果不至于和额度一起丢

> 踩过的坑，值得记住：这个接口在 2026-09 已改为 **SSE 流式**
> （`data: {"type":"delta","text":"…"}`）。按老前端快照写 `res.json()` 会抛
> `JSONDecodeError`——**而这一次调用已经扣了额度**。`ask_ai.py` 因此同时解析
> JSON 与 SSE，并把原始字节存盘。如果你要改这个脚本，别删这段逻辑。

额度耗尽时脚本返回 3 并正常退出，不重试、不注册新账号绕过限额。

## 8. 排错

| 症状 | 原因与处理 |
|---|---|
| `setup.sh` 报找不到 Python 3.9+ | `sudo apt install -y python3 python3-venv python3-pip`；或 `./setup.sh --python /path/to/python3.12` |
| 依赖装不上 / 超时 | 墙内用 `./setup.sh --mirror`；或手动指定 `PIP_INDEX_URL` |
| 图上中文变方块 | `sudo apt install -y fonts-noto-cjk`（RHEL：`wqy-zenhei-fonts`）。不影响数值与结构 |
| `ai_login.py` 失败 | 检查 `.env` 里的邮箱密码；若在墙内且 AI 站点需要代理，设 `HTTPS_PROXY` |
| 拉数据失败 | 币安需要代理：`.env` 里设 `HTTPS_PROXY=http://127.0.0.1:7890`。socks5 需先 `pip install PySocks` |
| `ask_ai.py` 返回 3 | 今日额度已用完，属正常。等次日 00:00 UTC 重置 |
| `ask_ai.py` 返回 1 且是 402 | 同上，额度耗尽 |
| `ask_ai.py` 报 JSONDecodeError | 接口又改形态了。看 `out/ai_raw_response.txt` 的原始报文再改解析 |
| cron 没触发 | `systemctl status cron`（RHEL 是 `crond`）；确认 `crontab -l` 有内容；看 `logs/cron.log` |
| cron 触发但没产出 | 看 `logs/run_YYYYMMDD.log`。cron 环境变量极简，脚本内部已自行加载 `.env` |
| 时区不对 | `install_cron.sh` 默认写 `CRON_TZ=UTC`；若 crond 不支持会自动换算本地时间 |
| 想换阈值做稳健性检查 | `swing_watch.py --theta 0.20` 对比 0.30 的结论是否一致 |
| 不确定环境是否正常 | `.venv/bin/python selftest.py`，47 项检查，全过再依赖结论 |

**日志轮转**：`logs/` 会一直增长（每天约几十 KB）。嫌大就加一条
`0 0 1 * * find <ai_structure 目录>/logs -name '*.log' -mtime +90 -delete`。

## 9. 方法论摘要（为什么这些数字可信）

这套分析相对「画几条线看趋势」的关键差别，都在下面四点里：

**① 非重叠子样本。** 连续取样会让名义样本虚高几十倍，置信区间完全是假的。
每个状态按「步长 ≥ 前瞻期限」贪心抽取非重叠观测，所有统计量都只在这个子样本上算。
7 天期限用 7 天步长，365 天期限用 365 天步长——这是 3,315 天数据里能得到 3 个独立
365 天观测的原因，也是为什么长期限结论必然稀少。

**② Wilson 区间而非正态近似。** 小样本下正态近似的置信区间会跑到 [0.9, 1.1] 这种
不可能的值。Wilson 不会。

**③ 单侧检验按观测偏离方向取尾。** 固定取上尾会把「明显偏空」的证据算成 p ≈ 0.96，
看起来「完全不显著」。按实际偏离方向取尾才是对的。

**④ 基准率是必须的对照组。** BTC 无条件上涨。不设对照的「看多」没有信息量——
7 天 P(涨) = 59% 听起来不错，但基准率就有 55%，增量只有 4 个百分点。

**⑤ 事件去重阈值随期限缩放。** 两个观测只有在「前瞻窗口重叠」时才是重复计数。
15 天期限下相隔 9 天的两段是独立的；365 天期限下则不是。
用固定阈值（例如 180 天）会在短期限上过度合并，把有效样本杀掉一大半。

## 10. 已知限制

说清楚这些，比假装没有更有用：

- **结构能回答「现在在哪」，不能可靠回答「接下来去哪」。** 报告里方向性结论大量是
  「含 50%，无法确认」——这是真实结果，不是没跑出来。**期限越短，基准率越接近 50%，
  信噪比越差**，这是算术约束，不是样本量问题。
- **θ 是选择，不是真理。** 0.30 是主口径，0.20 是稳健性口径。换阈值结论会变，
  所以两个都跑。
- **历史类比有幸存者偏差风险。** 「与今天最像的历史时段」是筛选出来的，
  样本天然偏向那些「后来走出来了」的案例。报告里给了事件数，事件少的期限请自行打折。
- **数据里有缺口。** 币安维护窗口会导致偶发的 K 线缺失（当前数据集有 19 处 >2 小时，
  最长 34 小时）。`nonoverlap` 与前瞻收益都按「bar 数」而非「真实小时数」计算，
  因此缺口处的时间跨度会略被低估。19 处合计约 100 小时，占 79,743 根样本的 0.1% 量级，
  对结论无实质影响，但值得知道。
- **时段划分固定 UTC，不随夏令时调整。** DST 会让欧/美边界漂移 1 小时，
  对第 1 节那张表的边界小时（13:00、16:00）有约 1 小时的模糊。对 14:00 的峰值结论无影响。
- **AI 对比不做仲裁。** 外部 AI 的解读和程序结论经常「方向一致但强度不一致」，
  这不是矛盾。两者的信息源、时间尺度、可证伪性都不同，并排放着看就好。
